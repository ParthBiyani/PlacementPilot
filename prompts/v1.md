# Prompt v1

Mirror of the `prompts` table row for `version = sha256(template + profile)`, kept here for git
diffability (see repo layout in `CLAUDE.md`). The actual hash is computed by the Crypto node inside
WF-2, at run time, from this exact template text with the profile block interpolated — this file is a
human-readable copy, not the source of truth n8n reads from.

**Model:** `claude-haiku-4-5-20251001`. **Temperature:** `0` — a scoring/classification task benefits
from low variance, and since this feeds a cache keyed on `(content_hash, prompt_version, model)`, a
volatile answer at cache-miss time gets pinned for the life of that cache entry regardless.

## System message template

The `{{...}}` placeholders are filled from `config.profile` (fetched via WF-L0 from
`preferences.json`) once per WF-2 run, then held constant across every posting scored in that run —
this is the "profile" half of `prompt_version`. The posting itself is passed separately as the user
message and is *not* part of the hash (that's what `content_hash` is for).

```
You are screening job postings for a specific candidate. Score how well each posting matches their profile and preferences.

CANDIDATE PROFILE:
{{summary}}

Skills: {{skills}}
Notable projects: {{projects}}
Graduating: {{graduation_year}}

RESPOND WITH STRICT JSON ONLY, matching exactly this shape, no other text, no markdown fences:
{
  "match_score": <integer 0-100>,
  "should_apply": <boolean>,
  "reason": "<string, at most 300 characters>",
  "missing_skills": ["<string>", ... at most 5 items],
  "deadline": "<string, exactly as stated in the posting (e.g. 'Rolling', '2026-09-15'), or null if the posting does not state one>",
  "eligibility": "<string, exactly as stated in the posting (e.g. 'Final year students, CGPA 7.0+'), or null if the posting does not state one>"
}

Scoring guidance:
- match_score reflects genuine fit: skills overlap, seniority match, domain relevance.
- should_apply is true only if match_score suggests a real, actionable opportunity.
- reason is a concise, specific justification a human could act on in five seconds.
- missing_skills lists skills the posting wants that the candidate's profile doesn't show; empty array if none.
- deadline and eligibility are extracted, never inferred: use null unless the posting text explicitly states one. Do not guess a deadline from posted_date, and do not infer eligibility from role seniority.
- When genuinely uncertain, score toward inclusion rather than exclusion -- a missed good match is a worse outcome than an extra alert.
```

## User message template

```
COMPANY: {{company}}

DESCRIPTION:
{{description}}
```

## Contract validated on every response (`db/schema.sql` `evaluations` table)

| Field | Rule |
|---|---|
| `match_score` | integer, 0–100 |
| `should_apply` | boolean |
| `reason` | string, ≤300 chars |
| `missing_skills` | array, ≤5 items |
| `deadline` | string or null |
| `eligibility` | string or null |

Invalid response → one retry with the parse/validation error appended to the user message → still
invalid → the row is flagged (`evaluations.invalid = true`) and persisted anyway, never silently
dropped. WF-5 (Phase 3) alarms on flagged rows once it exists; until then the flag itself is the record.

## Changelog

- **v1** (2026-08-14) — baseline, zero-shot. No results yet — `eval_runs` stays empty until Phase 7's
  200-posting labeled set exists.
- **v1** (2026-08-14, same day) — added `deadline`/`eligibility` extraction fields to the contract
  (nullable, extracted verbatim from the posting text, never inferred) after seeing the first real
  Discord alert and wanting that context in the message. This changes the rendered template text, so it
  also silently bumps `prompt_version` (the hash includes template + profile) -- expected, not a bug: any
  cached score under the old contract shape is correctly treated as stale and re-scored.
